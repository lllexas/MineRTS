# 2026-04-19 Entity Assembly Design

## 目的

这份文档用来整理接下来 `Warehouse / Lab / Entity` 这条线的设计共识。

今天 `SocialBox` 已经把一整套前后端链路打通了，接下来不应该再回到“先写一坨功能再慢慢猜抽象”的状态。

`Entity` 这条线的目标是：

- 定义实体资源在 VFS 中如何存在
- 定义科技树条目如何分发实体
- 定义静态原型、动态修改器、运行时执行 pack 之间的关系
- 给之后改造：
  - `Warehouse`
  - `Lab`
  - `.entity`
  - `.modifier`
  - 战斗前装配

提供统一设计依据。

---

## 一、痛点

### 1. `.entity` 很难被一个单一 SO 完整描述

实体类资源天然混着两种东西：

- 偏静态内容
  - sprite
  - 模型
  - 音效
  - 特效
  - 不变基础蓝图

- 偏动态内容
  - 科技加成
  - 数值词条
  - 修饰器
  - 阵营、关卡、装备等额外变化

如果把它们全部硬塞进一个 SO：

- 编辑方便，但结构会越来越臃肿
- 动态变化会污染静态原型
- 以后要做修饰器叠加、科技树增量修改、战斗前组装时，会很难拆

所以“实体是不是一个单 SO”本身就是第一个痛点。

### 2. 玩家仓库和科技树面对的不是同一种东西

玩家仓库关心的是：

- 玩家当前持有哪些可用实体
- 它们如何查看
- 它们如何在战斗阶段被真正实例化

科技树关心的是：

- 某个条目能不能研究
- 它研究后给玩家什么
- 它展示什么说明和预览

也就是说：

- `Warehouse` 关心“玩家已经拥有的实体资源”
- `Lab` 关心“尚未拥有、但可研究和分发的条目”

如果把二者都理解成同一种资源，会很容易把“科技树条目”和“实体本体”混掉。

### 3. 运行时执行与资源配置不是同一层

真正到了战斗阶段，单位生成不是“读一个配置然后马上生成”这么简单。

它更像：

1. 先拿到某个实体原型
2. 把修饰器逐层叠上去
3. 在战斗上下文中接收：
   - 阵营
   - 坐标
   - 召唤参数
4. 最终生成实体

这说明：

- 资源配置层
- 装配层
- 战斗执行层

不是同一层，不应该混写在一个节点里。

---

## 二、原理

### 1. `.entity` 是静态原型入口，不是全部真相

`Entity` 这一层最合理的理解，不是“一个文件描述一个单位的一切”，而是：

**一个实体原型入口。**

它至少应该能稳定承载那些偏静态、偏模板化的内容：

- 声效
- 光效
- sprite / 模型
- 不变基础蓝图

这部分用 `SO` 是合理的，也是方便的。

所以这条线的原理是：

- `EntitySO` 管静态原型
- 动态变化不要直接污染 `EntitySO`

### 2. 修改器是独立资源

各种增减益、科技加成、词条修正、场景修正，不适合全部塞回 `EntitySO`。

它们更适合作为独立资源存在：

- `json`
- `csv`
- 或以后别的轻量格式

它们的语义应该是：

- 接收当前实体 payload
- 修改其中部分字段
- 再把结果往后传

所以修改器的原理不是“另一个实体”，而是：

**对实体原型或实体运行参数的增量修正。**

### 3. 运行时真正执行的不是散件，而是装配后的 pack

如果实体生成过程需要：

- 基础原型
- 声光资源
- 数值修正器
- 战斗事件入口
- 位置参数注入

那么最终真正进入战斗逻辑的，最好不是一堆散件直接各自跑，而是：

**动态装配后的实体执行 pack。**

这意味着：

- 平时资源可以散装存在
- 真正进入战斗前，再根据玩家当前拥有内容、科技、修饰器，把它们拼成一个可执行 pack

这个 pack 再负责：

- 接收事件
- 收到位置参数
- 真正实例化单位

### 4. `LabEntry` 不是执行节点，而是前端条目

科技树条目和实体原型不是一回事。

`LabEntry` 更像：

- 可研究条目
- 解锁入口
- 展示卡片
- 分发钩子

因此它的重心应当是：

- `Query`
- 前端展示
- 解锁动作

而不是：

- 后台运行 `Execute`

它更像 `SocialBox` 中的前端交互资源，而不像一个战斗执行节点。

## 三、设计

## 1. 资源分层

当前建议至少分成三层：

### A. 静态原型层

候选资源：

- `EntitySO`

负责：

- 名称
- 图标
- sprite / 模型
- 音效
- 特效
- 基础数值蓝图

对应 VFS 资源：

- `.entity`

### B. 动态修正层

候选资源：

- `.modifier`

负责：

- 修改实体数值
- 添加或覆盖标签
- 施加科技/装备/环境修正

它更适合轻量文本格式：

- `json`
- `csv`

### C. 执行装配层

候选对象：

- 动态装配出来的 battle pack

负责：

- 把 `.entity` 作为基础 payload
- 串过若干 `.modifier`
- 接收事件和位置参数
- 最终实例化战斗单位

这一层不是静态资源模板，而是：

**战斗前装配出来的运行时 pack。**

---

## 2. `.entity`

### 核心判断

`.entity` 是资源原型入口。

它不是“玩家背包里已经活着的实例”，也不是“科技树条目”，而是：

- 一个静态原型
- 一个战斗生成链的起点

### 建议形态

- `EntitySO`
- `VFSResource(".entity", typeof(EntitySO))`

### Query

`Query` 用途：

- 仓库中查看实体信息
- 前台展示面板
- 显示：
  - 头像
  - 名称
  - 描述
  - 基础数值
  - 标签

也就是说，`.entity Query` 是仓库查看入口。

### Execute

`Execute` 只在战斗阶段有意义。

它的语义不是“展示自己”，而是：

- 把 `EntitySO` 作为 payload 注入后续执行链
- 或直接配合位置参数实例化单位

所以：

- 平时仓库查看主要走 `Query`
- 战斗中召唤才走 `Execute`

### 执行模式

`.entity` 对应的 pack 可以设计成一个循环等待型 pack：

- 起点等待外部事件
- 收到事件后拿位置参数
- 执行召唤
- 最后回到起点继续等待

这使得实体执行 pack 成为：

- 一个可重复使用的召唤模板
- 而不是一次性流程包

---

## 3. `.modifier`

### 核心判断

`.modifier` 负责修改当前实体 payload。

它不是实体本体，不需要承载全部资源，只关心：

- 哪些字段要怎么改

### 建议形态

- `json` / `csv`
- `VFSResource(".modifier", typeof(...))`

### Execute

`Execute` 语义非常直接：

- 读取当前 payload
- 修改数值
- 返回修改后的 payload

比如：

- 攻击 +10
- 血量倍率 1.2
- 加标签 `fire`
- 替换音效 key

### Query

`Query` 可以有，但不是第一优先级。

用途大概是：

- 在 Lab 或调试面板里显示修正内容
- 用于查看这个 modifier 到底改了什么

但就优先级来说，`.modifier` 的第一职责还是执行修正。

---

## 4. `.labentry`

### 核心判断

`.labentry` 是科技树条目。

它不是实体本体，不是修改器，也不是战斗执行节点。

它负责：

- 展示
- 预览
- 解锁
- 分发

### 建议形态

- `LabEntrySO`
- 其中直接引用：
  - `EntitySO`
  - 可能还包括描述、成本、前置条件、图标等

### Query

`.labentry Query` 才是核心。

它应当提供：

- 条目标题
- 描述
- 研究成本
- 是否已解锁
- 预览内容
- 前端解锁动作

这个前端动作应当最终落到领域 service / facade，而不是让 `.labentry` 自己伪装成后台执行节点。

### Execute

当前结论：

**`.labentry` 不需要正式的 `Execute`。**

原因是：

- 科技树条目本质是前端交互资源
- 真正的业务动作是“解锁后分发到仓库”
- 这个动作更适合由业务 facade/service 实现

### 解锁后的动作

建议行为：

- 把 `LabEntrySO` 引用的 `EntitySO`
- 包装成一个 `vfs.entity`
- 投递到玩家仓库

也就是说：

- `LabEntry` 负责“告诉前端可以解锁什么”
- `Warehouse / Entity` 负责“玩家实际获得了什么”

---

## 5. 仓库和科技树的关系

### 玩家仓库 pack

盛放：

- 玩家当前可用的 `vfs.entity`

面向：

- 查看
- 排序
- 选择
- 战斗前装载

### 科技树 pack

盛放：

- `vfs.labentry`

面向：

- 展示可研究内容
- 触发解锁
- 分发实体到仓库

所以：

- 科技树里存的是“入口条目”
- 仓库里存的是“已拥有实体”

二者不应继续混成一个概念。

---

## 6. 后续实现顺序

推荐顺序：

1. 先定 `EntitySO`
2. 再定 `LabEntrySO`
3. 给 `.entity` 做 `Query`
4. 给 `.labentry` 做 `Query`
5. 写一个最小 `EntityWarehouseFacade`
6. 让 `.labentry Query` 的解锁动作把 `EntitySO` 投递进仓库
7. 最后再做 `.entity Execute`
8. 再补 `.modifier Execute`
9. 最终把战斗前动态装配 pack 接上

这样可以避免一上来就陷入“战斗执行 pack 全部一次做完”的大泥潭。

---

## 八、空间模型决断

今天已经明确做出一个重要决断：

- 建筑继续格点
- 单位也保留格点束缚

这里不是从沉没成本出发，而是从玩法设计出发。

关键判断是：

**单位格点化不是技术妥协，而是位置博弈立场。**

它会强化这些东西：

- 进攻路径选择
- 卡位
- 包夹
- 宽度管理
- 路口争夺
- 前后排秩序
- 战场局部封锁

也就是说，格点束缚会让单位战斗更“硬”，更强调：

- 每一步位置都要付代价
- 每一次绕后、脱困、封路都更加明确

这条设计立场应当继续被保留，而不是在 `.entity` 开工前临时切去纯连续空间。

### 补充理解

需要区分两件事：

- 连续空间更自然
- 格点空间更强调位置博弈

当前项目的战斗目标，更偏向后者。

因此之后的 `.entity Execute`、移动、阻挡、召唤入口、战斗接口，都应当默认建立在：

**单位仍然是格点规则实体**

这个前提上。

---

## 九、下一期工程：群体移动优化

虽然单位保留格点束缚，但当前移动方式不能继续完全依赖“规划式移动”。

现在已有系统更偏：

- 路径规划
- 预约
- 格点目标推进

这能工作，但对于群体移动来说还不够。

下一期应重点优化：

- 友军与友军之间的局部响应式移动
- 编队内的让位、借道、顺滑交换
- 局部拥堵时的即时反应，而不是只等全局路径重算

也就是说，后续方向不是“去掉格点”，而是：

**在格点规则下，引入更强的响应式群体移动能力。**

一句话总结：

- 规则层继续保留格点
- 群体移动层减少对纯规划的依赖
- 让单位在保持位置博弈强度的同时，不至于显得过分死板

---

## 十、蓝图 SO 化迁移原则

### 目标

后续实体原型的正式来源，改为：

- `EntityBlueprintSO`

而不是继续依赖：

- `BlueprintRegistry` 里的硬编码注册表
- `EntityBlueprint` 这种中间纯数据总表

### 设计目的

这里的目的不是“把数据从代码抄进资源文件”这么简单，而是：

1. 让 `.entity` 资源自己直接持有原型 SO
2. 让战斗执行链在运行时直接拿到 `EntityBlueprintSO`
3. 让 `CreateEntity` 桥接层继续保留
4. 让后续 `.modifier` 可以继续基于 `BlueprintField` 覆写 ECS 字段

也就是说：

- 桥接层继续存在
- 蓝图来源改成 SO

### 明确边界

当前结论是：

- `CreateEntity(...)` 保留
- 新增 `CreateEntityFromSO(...)`
- 旧 `CreateEntityFromBlueprint(string bpKey, ...)` 先保留
- 旧 `BlueprintRegistry` 先不删，作为搬家兼容层

### 为什么旧注册表先不删

因为当前项目里仍有很多旧入口依赖：

- 建筑放置
- UI 显示
- 调试命令
- 工业系统的一些静态查询

所以当前阶段的正确策略不是“一刀切删掉”，而是：

- 新系统开始直接吃 `EntityBlueprintSO`
- 旧系统继续暂时吃 `BlueprintRegistry`
- 等迁移完成后，再把旧注册表整体退役

### 迁移顺序

建议顺序：

1. 先定义 `EntityBlueprintSO`
2. 给 `EntitySystem` 增加 `CreateEntityFromSO(...)`
3. 让未来 `.entity Execute` 直接调用这个新入口
4. 再逐步把旧建筑/UI/调试链从 `BlueprintRegistry` 迁走
5. 最后再处理旧 `EntityBlueprint` 与注册表的彻底退役

---

## 七、一句话总结

这条线最重要的判断不是“`.entity` 到底是不是一个 SO”，而是：

**把实体系统拆成：静态原型、动态修正、运行时装配。**

对应到资源协议上就是：

- `.entity` 管原型
- `.modifier` 管修正
- `.labentry` 管科技树入口
- 最终战斗中真正运行的是动态装配出来的实体执行 pack

这套设计既能保持编辑方便，也能给之后的仓库、科技树、战斗执行留出清晰边界。
